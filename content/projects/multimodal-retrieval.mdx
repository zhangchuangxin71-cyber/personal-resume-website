## 实现细节

项目包含数据筛选、模型微调、Top K 评估、视频编码、混合检索和服务化部署。通过消融实验比较分段时长与抽帧帧率，确定视频表示的参数组合。

### 工程落点

- 向量化能力独立成 `embedding_service`，同步文本编码和异步图片/视频编码共用同一套 API
- `picture/` 和 `video_retrieval/` 只负责检索，不再混入本地入库脚本
- 默认向量库是 Milvus，写库前先执行 `python -m embedding_service.milvus_init`
- 视频检索采用分段抽帧 + 注意力池化，不把整段视频粗暴压成单帧平均
- 文本检索用 BGE 稠密向量配合 SQLite FTS5 的 BM25 稀疏检索，再用 RRF 融合排名
- 图片、视频编码走异步任务，状态可查询，便于处理长任务和 OSS 资源

### 为什么要拆成这几层

如果把“编码、入库、检索、任务状态”混在一个脚本里，问题会非常难定位。这个项目把它们拆成了共享编码库、向量化服务和纯检索入口三层，既能独立部署，也能在 Milvus、FAISS 和本地调试之间切换。

## 最难的问题

### 视频表示不等于图片表示的简单平均

视频中的关键动作可能只出现几秒。分段采样保留时间范围，注意力池化避免关键帧在平均过程中被淹没，视频原始 Top1 命中率由 14% 提升到 20.6%。

### 排名优化必须被独立测量

编码和排序分阶段评估，避免把召回改善和融合算法混为一谈。加入双通道 RRF 后，视频排序 Top1 达到 38%，Top10 达到 73%。

## 交付与影响

- 支持万级视频素材批量入库
- 完成容器化部署、标准化 API 文档和可重复验收脚本
- 把同步文本编码与异步图片、视频编码统一成一套服务接口

## 反思与下一步

离线 Top K 指标反映检索质量，但不能完全代表真实编辑工作中的可用性。下一步可按人物、动作、场景和对白查询分别建立分桶评测，并观察每类证据的失败模式。
